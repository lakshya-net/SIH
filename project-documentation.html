1. Project Overview

Sanjeevni (named after the mythical healing herb from the Ramayana) is a comprehensive, centralized Government Electronic Health Record (EHR) and Hospital Management System designed for government hospitals across India. It provides a unified platform where patients, doctors, lab technicians, and hospital kiosks can interact with a single patient health record throughout their lifetime.

Core Vision: Every citizen of India gets a single Unique Health ID (HID) that follows them across all government hospitals. All medical data — visits, prescriptions, lab results, self-reported vitals, surgical history, vaccinations — is chained as "clinical nodes" in a lifetime timeline. After each treatment completes, the data is compacted into a summary, keeping the active database lean while preserving full historical context.

Key Highlights

  • 6 Role-Based Portals: Patient Portal, Kiosk Mode, Lab Portal, Doctor Clinical View, Doctor Prescription Builder, Patient Intake Wizard
  • AI-Powered Triage: Built-in clinical decision support engine that checks drug interactions, allergy cross-reactivity, polypharmacy risks, critical lab values, and vital sign abnormalities
  • Multilingual UI: Supports English, Hindi, and Bengali through a DOM-level translator and i18n framework
  • Treatment Compaction: Unique data management approach where completed treatment chains are compressed into summaries, maintaining a clean active database
  • Voice Input: Kiosk mode supports voice-based patient registration with multilingual speech transcription
  • OCR Prescription Scanning: Upload prescription images and extract medications using Google Gemini AI
  • Neon PostgreSQL: Serverless cloud database with automatic schema creation and mock data seeding

2. Problem Statement & Motivation

The Problem

  • Government hospitals in India still rely on paper-based records or fragmented digital systems
  • Patient records are siloed within individual hospitals — there is no central repository
  • Patients visiting multiple hospitals must carry physical files or repeat tests
  • Doctors lack a complete medical history when treating patients from other hospitals
  • Language barriers prevent effective communication in multilingual India
  • No standardized system for AI-assisted clinical decision support in government hospitals

Our Solution

Sanjeevni creates a unified, lifetime health record for every patient with a Unique Health ID. The system captures data from multiple entry points (kiosk registration, patient self-report, doctor consultations, lab results, prescription scanning) and chains them into a coherent clinical timeline. An AI triage engine provides real-time clinical decision support to doctors, and treatment compaction ensures the system remains performant over decades of patient history.

6. End-to-End Workflow

Component 1: Initial Patient Input (Point of Entry)

  1. Walk-in Registration: Patient arrives at hospital kiosk → speaks details in their language → system auto-fills registration form → generates Unique Health ID
  2. Identity Verification: OTP-based or National ID (Aadhaar) verification audit record is created
  3. Full Registration: Patient fills 7-step intake wizard (demographics, conditions, surgeries, vaccines, medications, allergies, lifestyle)
  4. Self-Report: Patient can submit home vitals (BP, sugar, temperature) through the Patient Portal

Component 2: Recurring Input

  1. Hospital Lab: Lab technician searches patient by name or HID → enters test parameters → uploads diagnostic files → submits results to active doctor session
  2. Doctor Consultation: Doctor enters patient's HID → reviews complete medical history → AI triage engine analyzes and provides clinical decision support
  3. Prescription: Doctor dictates or scans prescription → reviews extracted medications → saves to patient record
  4. Document Upload: MRI, X-Ray, CT Scan reports uploaded from hospital systems

Component 3: Data Storage & Compaction (USP)

  1. Chained Instances: Each patient interaction (visit, lab, prescription, self-report) creates a "clinical node" chained to the patient's record
  2. Active Treatment: While treatment is ongoing, all detailed data (vitals, prescriptions, lab results, documents) is preserved in the database
  3. Treatment Completion: Doctor declares treatment ended → system compacts the treatment chain:
    • Detailed clinical nodes, vitals, prescriptions, lab reports, and documents are deleted from the active database
    • A treatment summary node is created with diagnosis, notes, key findings, and medication names
    • The encounter status changes from "Active" to "Completed"
  4. Lifetime History: Compacted summaries remain in the patient's timeline for future reference

Component 4: Patient History Fetching

  1. Doctor logs in → enters patient's Unique Health ID
  2. System pulls complete medical history: all visits, lab results, prescriptions, treatment summaries
  3. Doctor can review history, add prescriptions, or end the current treatment

8. AI Triage Engine

The triage engine (triageEngine.ts) is a rule-based clinical decision support system that runs entirely in-memory (no external API calls). It analyzes the consultation payload and generates:

8 Risk Categories Analyzed

  1. Allergy Risk Checks: Direct drug-allergy matching, cross-reactivity detection (e.g., Penicillin → Amoxicillin), severe allergy alerts
  2. Drug Interaction Checks: 10 known drug pairs checked (e.g., Warfarin + Aspirin = major bleeding risk)
  3. Polypharmacy Warning: Flags when patient has ≥5 concurrent medications
  4. Chronic Condition Monitoring: Checks for unmedicated conditions, worsening HbA1c, elevated blood pressure
  5. Vital Signs Assessment: Hypertensive emergency (>180/120), critical SpO2 (<90%), high fever (>39.5°F)
  6. Lab Result Analysis: 10 critical thresholds for glucose, HbA1c, cholesterol, hemoglobin, creatinine, WBC, platelets, sodium, potassium
  7. Care Recommendations: Prioritized actionable items based on findings
  8. Clinical Summary: Weighted risk score with severity levels (critical/high/moderate/low/informational)

💡 Viva Point: Why Rule-Based Instead of ML?

The triage engine uses a deterministic rule-based approach rather than machine learning for several reasons:

  • Explainability: Every alert has clear evidence and reasoning that can be audited by doctors
  • Reliability: No risk of model hallucination or unpredictable outputs in critical medical scenarios
  • Compliance: Deterministic rules are easier to validate for medical device regulations
  • Performance: Runs in milliseconds with no external API calls

9. Treatment Compaction (Unique Selling Point)

The Core Innovation: After any treatment or procedure is completed, the entire chain of clinical data is compressed. Relevant information for future reference is extracted and stored as a summary node, while the detailed treatment chain is deleted from the active database.

How Treatment Compaction Works

  1. Save Prescription: Doctor saves prescriptions → data is persisted → encounter remains Active → no data is deleted
  2. Complete Treatment: Doctor clicks "Declare Treatment Ended & Create Summary"
    • A single PostgreSQL transaction is initiated
    • All prescriptions for the encounter are saved
    • A treatment_summaries row is created with diagnosis, notes, and key findings
    • A "Treatment Summary" clinical node is created in the patient's timeline
    • Detailed data is deleted: clinical nodes, vitals, lab reports/results, document metadata, prescriptions
    • Encounter status is updated from "Active" to "Completed"
    • Encounter diagnosis and clinical notes are set to NULL (preserved only in summary)

Why This Matters

  • Performance: Active database stays small — only current treatments have full detail
  • Storage Efficiency: Detailed data from completed treatments doesn't accumulate indefinitely
  • Historical Preservation: Treatment summaries contain the essential information for continuity of care
  • Privacy: Reduces the attack surface by minimizing stored sensitive data

10. OCR & Prescription Extraction

How It Works

  1. Doctor uploads a prescription image (JPEG, PNG, WEBP — max 10MB)
  2. Image is sent to /api/ocr endpoint as FormData
  3. Server converts image to base64 and sends to Google Gemini 3.6 Flash with a structured prompt
  4. Gemini analyzes the image and returns JSON with extracted medications: 
    {
  "rawText": "Full OCR text...",
  "medications": [
    { "medicineName": "Paracetamol", "dosage": "650mg", "frequency": "TDS", "duration": "5 days" }
  ]
}
  5. Medications are auto-populated in the prescription builder for doctor review
  6. Doctor can edit, add, or remove medications before saving

AI Summarization (/api/summarize)

Uses Gemini to generate patient-friendly summaries of medical reports. Takes raw medical text and returns a simplified explanation suitable for patients.

11. Multilingual Support

Dual Translation Approach

1. React i18n Context (for Kiosk Mode)

  • I18nProvider wraps the application with language context
  • useI18n() hook provides t(key) translation function
  • Supports English (en), Hindi (hi), Bengali (bn)
  • Language persisted in localStorage with key govehr-language
  • Kiosk-specific translations in mockData.ts

2. DOM-Level Translator (for Full Page Translation)

  • DomTranslator component walks the rendered DOM and replaces English text with Hindi translations
  • Uses a TreeWalker to iterate over all text nodes
  • Pre-sorted dictionary (longest key first) for greedy substring matching
  • Protected from translating: inputs, code blocks, SVG, doctor-facing sections (data-no-translate attribute)
  • MutationObserver integration keeps translations in sync with React re-renders
  • Patient data (names, IDs, medical values) are never translated because they don't appear as exact dictionary keys

💡 Viva Point: Why DOM-Level Translation?

The DOM translator was chosen for full-page translation because:

  • It translates everything without modifying React source code
  • Works with dynamically rendered content via MutationObserver
  • Doctor-facing sections are excluded via data-no-translate attribute — ensuring medical terminology stays in English
  • Patient data (names, IDs, phone numbers) are automatically excluded since they never match dictionary keys

12. Identity Verification

The IdentityVerification component provides two verification methods:

  • OTP Verification: Simulated OTP sent to phone number → enter code → verification recorded
  • National ID Verification: Aadhaar-based identity verification with hash storage

Both methods create audit records in the identity_verifications table with method, phone last 4 digits (or hashed national ID), and timestamp. The verification state is managed globally via Zustand and persists across portal switches.

15. Viva Preparation — Frequently Asked Questions

Q1: What is the problem your project solves?

Government hospitals in India use fragmented, paper-based systems. Patients visiting multiple hospitals must carry physical files or repeat tests. There is no centralized repository for lifetime health records. Sanjeevni solves this by creating a unified EHR system with a Unique Health ID for every patient, enabling doctors to access complete medical history across all government hospitals.

Q2: What is your Unique Selling Point (USP)?

Treatment Compaction. Unlike traditional EHR systems that accumulate data indefinitely, Sanjeevni compresses completed treatment chains into summary nodes. This keeps the active database lean (only current treatments have full detail) while preserving essential information for continuity of care. It's a novel approach to balancing data completeness with system performance.

Q3: How does the AI Triage Engine work?

It's a deterministic rule-based engine that analyzes 8 categories: drug interactions, allergy cross-reactivity, polypharmacy risks, chronic condition monitoring, vital sign assessment, lab result analysis, and care recommendations. It runs entirely in-memory with no external API calls, ensuring sub-millisecond response times and full explainability for medical audit trails.

Q4: How do you handle multilingual support?

Dual approach: (1) React i18n context for Kiosk Mode with 3 languages (English, Hindi, Bengali), and (2) a DOM-level TreeWalker translator that walks the rendered page and replaces English text with Hindi translations without modifying React source code. Doctor-facing sections are excluded via data-no-translate attributes, and patient data is automatically excluded since it never matches dictionary keys.

Q5: Why PostgreSQL and not MongoDB?

Health records have strong relational integrity requirements — patients have encounters, encounters have prescriptions and lab results, prescriptions belong to specific encounters. PostgreSQL's ACID transactions ensure atomicity for multi-table operations like treatment compaction. JSONB columns provide flexibility for variable-structured data (allergies, emergency contacts) while maintaining relational integrity where needed.

Q6: How does the OCR prescription scanning work?

Doctors upload a prescription image (JPEG/PNG/WEBP). The server sends it to Google Gemini 3.6 Flash (multimodal AI) with a structured extraction prompt. Gemini returns JSON with extracted medications (name, dosage, frequency, duration). The medications are auto-populated in the prescription builder for doctor review and editing before committing to the database.

Q7: How do you ensure data security and privacy?

  • Identity verification creates audit trails (OTP/National ID)
  • Treatment compaction reduces stored sensitive data after completion
  • Server-side API keys never exposed to the client (Gemini key via header, not URL)
  • Medical documents stored in S3 with controlled access
  • Doctor-facing sections are protected from translation (data-no-translate)
  • Phone verification and national ID hashing for identity protection

Q8: How does the system scale?

  • Neon PostgreSQL: Serverless database that scales automatically with connection pooling (max 10 connections, idle timeout 30s)
  • Treatment Compaction: Keeps active data volume bounded — completed treatments are compressed to summaries
  • Database Indexes: Optimized composite indexes on (patient_id, date) for fast timeline queries
  • Lazy Initialization: Database is created on first request, not at build time
  • S3 Storage: Medical documents stored in scalable object storage, not the database

Q9: What technologies did you use and why?

  • Next.js 14: Full-stack framework with API routes, server components, and excellent TypeScript support
  • Zustand: Lightweight state management (no boilerplate, easy debugging, single store for all 6 portals)
  • Tailwind CSS: Rapid UI development with consistent design system
  • Radix UI: Accessible, unstyled primitives (WCAG compliant)
  • Neon PostgreSQL: Serverless, free tier, compatible with standard pg driver
  • Google Gemini: Free tier for OCR and summarization, multimodal capabilities

Q10: What would you improve in the future?

  • Real Web Speech API integration for actual voice recognition in Kiosk Mode
  • DigiLocker API integration for automatic Aadhaar-based document fetching
  • End-to-end encryption for patient data in transit and at rest
  • Integration with real DICOM viewers for medical imaging (X-Ray, MRI, CT)
  • Mobile app (React Native) for patient portal access
  • Real-time notifications via WebSocket for lab result delivery
  • Role-based access control (RBAC) with hospital-level permissions
  • Analytics dashboard for hospital administrators

Q11: Explain the data flow for a typical patient visit.

Flow: Patient registers at kiosk (voice or form) → HID generated → Vitals recorded → Doctor selects patient → AI triage runs → Lab tests ordered → Lab technician enters results → Results appear in doctor view → Doctor creates prescription (voice/OCR/manual) → Treatment completed → Data compacted → Summary node created → Patient can view lifetime timeline in portal.

Q12: How does state management work across 6 portals?

Zustand provides a single global store (useAppStore) shared by all 6 portals. The store holds: current role (which portal is active), patient data, encounters, lab reports, timeline, prescriptions, clinical notes, and OCR text. Portal switching is done by changing currentRole — no page reload needed. On app load, loadPersistedState() fetches data from /api/state to hydrate the store from the database.
